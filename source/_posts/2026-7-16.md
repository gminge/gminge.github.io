### **API 前置条件缺失**（missing precondition check）类漏洞

程序在调用某个 API 或执行某个关键操作之前，没有检查必须满足的条件，导致攻击者可以在“不应该发生”的状态下调用它，从而触发安全问题。

它属于一种**逻辑漏洞（Logic Vulnerability）**，不是传统的内存破坏漏洞（如 UAF、栈溢出），更多出现在**软件接口设计、权限控制、状态管理、资源管理**中。

常见漏洞类型

类型1：权限检查缺失

类型2：状态检查缺失

类型3：生命周期检查缺失

类型4：资源状态检查缺失

# `count_lengths()` 函数分析

## 函数签名

```c
static inline void count_lengths(uint16_t *lens, int codes, uint16_t *count)
```

## 参数说明

| 参数          | 类型           | 方向  | 含义                                                                                                            |
| ----------- | ------------ | --- | ------------------------------------------------------------------------------------------------------------- |
| **`lens`**  | `uint16_t *` | 输入  | 码长数组，`lens[i]` = 符号 `i` 的 Huffman 码长（合法值范围：0 ~ MAX_BITS(15)）。`lens[i] = 0` 表示该符号不出现在当前数据块中                    |
| **`codes`** | `int`        | 输入  | `lens[]` 数组中符号的总数。<br>• `CODES` = 19（CLENS 码长表的符号数）<br>• `LENS` = 286（字面量/长度码的符号数）<br>• `DISTS` = 32（距离码的符号数） |
| **`count`** | `uint16_t *` | 输出  | 直方图数组，`count[len]` = 码长为 `len` 的符号个数。数组大小为 `MAX_BITS + 1 = 16`（下标 0..15）                                      |

## 函数体

```c
// inftrees.c: line 192-205
static inline void count_lengths(const uint16_t *lens, unsigned codes, uint16_t *count) {
    for (unsigned sym = 0; sym < codes; sym++)
        count[lens[sym]]++;  // <-- [BUG] 若 lens[sym] > MAX_BITS(15)，count[16]++ 越界写入
}
```

## 功能

遍历所有符号的码长，统计每种码长（0..15）出现了多少次，结果存入 `count[]` 直方图。

**这是构建 Huffman 解码表 `zng_inflate_table()` 的第一步。**

---

## 调用上下文（完整流程）

`zng_inflate_table()` 负责根据给定的码长数组，构建 Huffman 解码查找表。其核心分为四个步骤：

```
                          ┌──────────────────────┐
      lens[0..codes-1]───▶│ 符号的码长            │  输入：每个符号的 Huffman 码长
                          └──────────┬───────────┘
                                     │
                                     ▼
              ┌──────────────────────────────────┐
              │ Step 1: count_lengths(lens,       │
              │         codes, count)             │
              │ → count[1..15] 直方图             │
              │   统计每种码长的符号个数            │
              └──────────────┬───────────────────┘
                             │
                             ▼
              ┌──────────────────────────────────┐
              │ Step 2: 前缀和 offs[]              │
              │    offs[1] = 0                    │
              │    offs[len+1] = offs[len]        │
              │                + count[len]       │
              │ → 每种码长在排序表中的起始偏移      │
              └──────────────┬───────────────────┘
                             │
                             ▼
              ┌──────────────────────────────────┐
              │ Step 3: 按码长排序符号             │
              │    for each sym:                  │
              │      if lens[sym] != 0:           │
              │        work[offs[lens[sym]]++]    │
              │          = sym                    │
              │ → work[] = 按码长升序排列的符号    │
              └──────────────┬───────────────────┘
                             │
                             ▼
              ┌──────────────────────────────────┐
              │ Step 4: 大循环构建 Huffman 解码表  │
              │    根据 work[] 生成 table[]        │
              │    填充 code 结构体条目            │
              └──────────────────────────────────┘
```

### completeness 检查（Step 1 之后）

在 `count_lengths()` 执行完毕后，`zng_inflate_table()` 使用 `count[]` 进行 Huffman 树的合法性检查：

```c
// inftrees.c: line 234-242
left = 1;
for (len = 1; len <= MAX_BITS; len++) {
    left <<= 1;
    left -= count[len];
    if (left < 0) return -1;   // over-subscribed：码长分配不可能
}
if (left > 0 && (type == CODES || max != 1))
    return -1;                  // incomplete：存在未覆盖的码字空间
```

这个循环从 `len=1` 遍历到 `len=15`，**不包括 `count[16]`**，如果攻击者通过 `lens[sym]=16` 污染了 `count[16]`，该值将**完全绕过 completeness 检查**。

---

## 具体示例

假设要编码 8 个符号（`codes = 8`），它们的码长分别为：

```
符号索引:  0    1    2    3    4    5    6    7
lens[]:   [2,   3,   3,   4,   4,   1,   0,   2]
          ↑
         符号0 需要 2 位编码
```

### 执行 `count_lengths(lens, 8, count)` 后：

```
count[0] = 1    ← 符号6 (lens[6]=0, 该符号不出现在数据中)
count[1] = 1    ← 符号5 (1位码)
count[2] = 2    ← 符号0, 符号7 (2位码)
count[3] = 2    ← 符号1, 符号2 (3位码)
count[4] = 2    ← 符号3, 符号4 (4位码)
count[5] = 0
...
count[15]= 0
```

### 后续 `left` 校验推演：

```
len=1: left = 1*2 - 1 = 1   (1个1位码字空间, 用了1个)
len=2: left = 1*2 - 2 = 0   (2个2位码字空间, 用了2个)
len=3: left = 0*2 - 2 = -2  → 返回 -1！over-subscribed
```

**`-1 (INCOMPLETE)` 错误的含义**：Huffman 码字空间不足。需要 2 个 3 位码，但前面只用掉了 1 个 1 位码（`0b0`），其子树下只有 2 个 3 位码空间（0b100, 0b101），还需留出空间给 4 位码，算法判定此码长分配**不可能**。

---

## `lens[]` 值为 0 的含义

| 值        | 含义                                            |
| -------- | --------------------------------------------- |
| `0`      | 该符号**不出现在当前数据块中**（deflate 动态 Huffman 编码的标准语义） |
| `1 ~ 15` | 该符号使用对应位数的 Huffman 编码                         |
| `16`（非法） | **超出 MAX_BITS(15)**，触发 count 越界写入             |

在 `count_lengths` 中 `count[0]++` 记录了"不出现"符号的个数。该计数不参与 completeness 检查（循环从 `len=1` 开始），也不参与 `offs[]` 前缀和计算。

## 漏洞分析

### 栈内存布局

在 `zng_inflate_table()` 函数中，两个局部数组相邻分配在栈上：

```
uint16_t count[MAX_BITS+1];   // count[0..15] —— 16 个 uint16_t
uint16_t offs[MAX_BITS+1];    // offs[0..15]  —— 16 个 uint16_t，紧接 count
                               //
                               // count[16] 越界地址 === offs[0] ！！
```

### 触发条件

当 `lens[sym] = 16`（超出 MAX_BITS = 15）时：

```c
count[lens[sym]]++;   // count[16]++ → 实际写入 offs[0]++
```

#### 必要前置条件：`lens[]` 中如何出现 > 15 的值

`zng_inflate_table()` 的函数注释（第 195-198 行）明确写道：

> *This routine assumes, but does not check, that all of the entries in lens[] are in the range 0..MAXBITS. **The caller must assure this.***

换言之，**调用者**有责任保证 `lens[]` 中的值合法。分析所有调用路径：

##### 路径 1：从合法 deflate 流解码（正常路径）— **不可触发**

`zng_inflate_table()` 的合法调用链位于 `inflate.c` 的 `LENLENS` 和 `CODELENS` 状态：

```
LENLENS 状态 (line 822-826):
  state->lens[order[state->have++]] = (uint16_t)BITS(3);
  // BITS(3) 范围为 0~7，永远不会 > 15 ✓

CODELENS 状态 (line 842-886):
  解码 CLENS Huffman 表得到 here.val:
  ├─ here.val < 16 → state->lens[state->have++] = here.val;  // 0~15 ✓
  ├─ here.val = 16 → len = state->lens[state->have - 1];     // 重复前一个 ≤15 的 lens ✓
  ├─ here.val = 17 → len = 0;                                // ✓
  └─ here.val = 18 → len = 0;                                // ✓
```

在**合法 deflate 数据流中，`state->lens[]` 的所有值都被限制在 0~15 范围内**，无法触发越界。

##### 路径 2：直接调用 `zng_inflate_table()` 并传入恶意 lens[] — **可触发（PoC 场景）**

如果攻击者能够绕过头文件封装、直接调用 `zng_inflate_table(LENS, lens, 286, ...)`，并在 `lens[]` 中嵌入值 16，则可在**不经过任何 deflate 流解析逻辑**的情况下触发越界。这是 PoC (`poc_stage_a.c`) 使用的方式：

```c
// PoC 示例
uint16_t lens[286] = {0};
lens[283] = 16;  // 恶意码长
zng_inflate_table(LENS, lens, 286, &table, &bits, work);
```

##### 路径 3：通过 CLENS Huffman 表"有毒解码"间接触发 — **理论可行**

虽然在合法流中 `here.val` 不会直接输出 > 15，但 CLENS 的码长表 `state->lens[0..18]` 先经过 `zng_inflate_table(CODES, ...)` 构建成 lencode 表。如果攻击者能够：

1. 先用其他手段污染 `state->lencode` 表（如内存损坏、堆溢出等）
2. 使得后续 CODELENS 解码时 `here.val` 被解为 16~255 之间的某个值

则 `state->lens[state->have++] = here.val` 可能写入 > 15 的值，进而在后续调用 `zng_inflate_table(LENS, ...)` 时触发 count 越界。

##### 路径 4：通过 `nlen` / `ndist` 字段溢出 — **理论可行**

deflate 头中的 HLIT 和 HDIST 字段分别指定 LENS 和 DISTS 符号数：

- HLIT（5 位）：字面量/长度码数 = HLIT + 257，最大 286
- HDIST（5 位）：距离码数 = HDIST + 1，最大 32

如果攻击者在 deflate 流头中设置了合法的 HLIT/HDIST（不触发错误），但同时在后面的码长数据中通过某种手段使 `state->lens[]` 在索引 ≥ 对应 `codes` 计数的位置被填充为 > 15 的值，虽然这些条目不参与解码，但它可能影响 `count_lengths()` 的遍历范围。

#### 触发条件总结

| 条件                                        | 可行性     | 说明                                   |
| ----------------------------------------- | ------- | ------------------------------------ |
| **合法 deflate 流**                          | ❌ 不可行   | deflate 流解析路径中所有 lens 赋值都被限制在 0~15   |
| **直接调用 `zng_inflate_table()` 传恶意 lens[]** | ✅ 可行    | 需要攻击者能直接调用该内部函数（PoC 场景）              |
| **CLENS Huffman 表中毒**                     | ⚠️ 理论可行 | 需要先有其他漏洞污染 lencode 表，再触发 CODELENS 解码 |
| **内存损坏先于 `count_lengths()`**              | ⚠️ 理论可行 | 需要先有其他漏洞（堆/栈溢出）修改 `state->lens[]` 的值 |

> **核心结论**：该漏洞在正常 deflate 数据流解析路径中**不可触发**。它本质上是 **API 前置条件缺失**（missing precondition check）类漏洞，仅当调用者未遵守"lens[] 所有值必须 ≤ MAX_BITS"这个未在代码中强制执行的前置条件时，才会引发栈越界。由于 `zng_inflate_table()` 是 `Z_INTERNAL` 可见性的内部函数，直接暴露给外部攻击者的面较小，但如果与内存损坏漏洞串联，可以作为利用链中的一环。

### 攻击链

```
1. 攻击者构造 lens[] 包含 lens[sym] = 16 的条目
       ↓
2. count_lengths() → count[16]++ → 写入 offs[0]，污染前缀和
       ↓
3. completeness check 只遍历 len=1..15，遗漏 count[16]
   → 恶意 lens[] 通过合法性验证
       ↓
4. offs[16] 未在前缀和循环中初始化（循环只到 MAX_BITS-1）
   → work[offs[16]] 指向未受控的内存
       ↓
5. work[] 越界写入 → 污染后续构建的 Huffman 解码表
       ↓
6. inffast decode 消费端读取被污染的 table 条目
   → 越界访问 lbase[] / lext[] 等静态数组
```

---

## 修复建议

### 方案 A：在 `count_lengths()` 入口添加 bounds check

```c
static inline void count_lengths(const uint16_t *lens, unsigned codes, uint16_t *count) {
    for (unsigned sym = 0; sym < codes; sym++) {
        unsigned len = lens[sym];
        if (UNLIKELY(len > MAX_BITS))
            return;            // 或设置全局错误标记
        count[len]++;
    }
}
```

### 方案 B：在 `zng_inflate_table()` 入口提前校验

```c
// zng_inflate_table() 函数开头
for (unsigned sym = 0; sym < codes; sym++) {
    if (lens[sym] > MAX_BITS)
        return -1;            // 拒绝非法码长
}
```

**推荐方案 A + B 结合**：防御性编程，两层防护。方案 A 防止 `count_lengths` 被其他潜在调用者滥用；方案 B 为 `zng_inflate_table` 提供入口级保护。

# `inflateCopy` 函数分析及与 `count_lengths` 的传参关系

## 函数签名与位置

- **位置：** `inflate.c:1380-1414`
- **可见性：** `Z_EXPORT`（公开 API）
- **原型：**
  ```c
  int32_t Z_EXPORT PREFIX(inflateCopy)(PREFIX3(stream) *dest, PREFIX3(stream) *source);
  ```

## 功能概述

`inflateCopy` 的作用是**深度复制**一个 inflate 解压流的状态到另一个流：

1. 复制 `z_stream` 结构体本身的全部字段
2. 分配新的 `window` + `state`（通过 `alloc_inflate()`）
3. 完整复制 `inflate_state` 结构体（`memcpy`）
4. **重定位内部指针**：`lencode`、`distcode`、`next`（它们指向 `codes[]` 数组内部）
5. 复制滑动窗口数据

## 完整源码

```c
int32_t Z_EXPORT PREFIX(inflateCopy)(PREFIX3(stream) *dest, PREFIX3(stream) *source) {
    struct inflate_state *state;
    struct inflate_state *copy;

    /* check input */
    if (inflateStateCheck(source) || dest == NULL)
        return Z_STREAM_ERROR;
    state = (struct inflate_state *)source->state;

    /* copy stream */
    memcpy(dest, source, sizeof(PREFIX3(stream)));

    /* allocate space */
    inflate_allocs *alloc_bufs = alloc_inflate(dest);
    if (alloc_bufs == NULL)
        return Z_MEM_ERROR;
    copy = alloc_bufs->state;

    /* copy state */
    memcpy(copy, state, sizeof(struct inflate_state));
    copy->strm = dest;
    if (state->lencode >= state->codes && state->lencode <= state->codes + ENOUGH - 1) {
        copy->lencode = copy->codes + (state->lencode - state->codes);
        copy->distcode = copy->codes + (state->distcode - state->codes);
    }
    copy->next = copy->codes + (state->next - state->codes);
    copy->window = alloc_bufs->window;
    copy->alloc_bufs = alloc_bufs;

    /* window */
    memcpy(copy->window, state->window, INFLATE_ADJUST_WINDOW_SIZE((size_t)state->wsize));

    dest->state = (struct internal_state *)copy;
    return Z_OK;
}
```

## inflate_state 结构体中与 `count_lengths` 相关的字段


## inflateCopy 的调用时机与 state->mode 状态

`inflateCopy` 可在解压过程的任意时刻被调用——**对 `state->mode` 没有限制**。以下场景至关重要：

### 场景 A：复制时处于 CODELENS 状态（最危险）

```
外部调用 inflate() → 状态机进入 TABLE → LENLENS → CODELENS
   ↓ (只填充了部分 lens[]，have < nlen + ndist)
外部调用 inflateCopy()  ← 此时 state->have 可能小于 nlen + ndist
   ↓ (复制所有字段，包括部分填充的 lens[])
在 copy 上继续调用 inflate()
   ↓ (继续 CODELENS 循环，合并攻击者后续的输入)
state->lens[] 被完全填充
   ↓
调用 zng_inflate_table(LENS, state->lens, state->nlen, ...)
   ↓
调用 count_lengths(state->lens, state->nlen, count)
   → lens[] 和 codes(nlen) 都来自被完全复制的 state
```

### 场景 B：复制时处于 LEN 状态（建表已完成）

```
外部调用 inflate()
   → TABLE → LENLENS → CODELENS → 建表完成 (LENS + DISTS 表已构建)
   → mode = LEN_
外部调用 inflateCopy()
   → lencode、distcode、next 指针通过重定位映射到 copy->codes[]
   → lens[] 数组中的值保留（但已不再使用，建表已完成）
在 copy 上继续调用 inflate()
   → 使用重定位后的 lencode/distcode 解码
   → 如果重定位计算错误，将读取越界的 code 条目
```

## inflateCopy 指针重定位中的安全问题

### 问题 #1：`next` 指针无边界检查

```c
copy->next = copy->codes + (state->next - state->codes);
```

**与 `lencode/distcode` 的边界检查对比：**

```c
// lencode/distcode 有边界检查（虽然存在 < vs <= 问题）
if (state->lencode >= state->codes && state->lencode <= state->codes + ENOUGH - 1) {
    copy->lencode = copy->codes + (state->lencode - state->codes);
    copy->distcode = copy->codes + (state->distcode - state->codes);
}

// next 完全无边界检查！
copy->next = copy->codes + (state->next - state->codes);
```

如果 `state->next` 已经因为 `count_lengths` 的 OOB → `offs[]` 污染 → `work[]` 越界 → 建表大循环中 `next` 跳转到异常位置，那么：

1. `copy->next` 将保留一个指向 `copy->codes` 数组之外的野指针
2. 后续在 copy 上调用 inflate() 时，如果触发新的动态块解码，`zng_inflate_table()` 会从 `copy->next` 指向的越界地址写入 Huffman 表条目
3. **这将导致堆越界写入**

### 问题 #2：`lencode` 边界检查的上界错误

```c
state->lencode <= state->codes + ENOUGH - 1
```

`codes[ENOUGH]` 的有效索引范围是 `[0, ENOUGH-1]`。检查使用 `<= codes + ENOUGH - 1` 意味着当 `lencode == codes + ENOUGH` 时会被认为合法，但实际上已经越界一个 `code` 元素。

### 问题 #3：`lens[320]` 的内容被完全复制

```c
memcpy(copy, state, sizeof(struct inflate_state));
```

`lens[320]` 包含在内。如果在 CODELENS 状态复制（`have` 未达到 `nlen + ndist`），部分 lens 条目来自 source 流的先前输入，部分为未初始化/历史残留值。**这些值在 copy 上继续 inflate 时将被传入 `count_lengths(lens, nlen, count)`**。

如果 lens 中包含 >MAX_BITS(15) 的值（无论来源），`count_lengths` 将发生 OOB 写入。

## inflateCopy 与 count_lengths 漏洞的串联利用

### 利用链

```
┌────────────────────────────────────────────────────────────────┐
│ Step 1: 攻击者构造恶意 deflate 数据流                            │
│         数据流包含:                                              │
│         (a) 合法的动态 Huffman 块头部 (HLIT, HDIST, HCLEN)        │
│         (b) 部分填充的 CODELENS 数据（在中间某个位置结束输入）      │
│         → inflate() 停在 CODELENS 状态，have < nlen + ndist      │
└────────────────────────────┬───────────────────────────────────┘
                             ↓
┌────────────────────────────────────────────────────────────────┐
│ Step 2: 攻击者调用 inflateCopy(dest, source)                     │
│         → copy->lens[0..have-1] 包含已解码的部分码长              │
│         → copy->lens[have..319] 为 memcpy 复制的原始 state 残留值 │
│         → 如果残留值中包含 >15 的值 ← 可通过第一种攻击污染 state    │
└────────────────────────────┬───────────────────────────────────┘
                             ↓
┌────────────────────────────────────────────────────────────────┐
│ Step 3: 在 copy 上继续调用 inflate()，提供新的输入数据             │
│         → CODELENS 循环继续填充 copy->lens[have++]               │
│         → 正常路径: 所有新填充的值在 0~15 范围                     │
│         → 但攻击者可利用 RLE 解码 (here.val==16/17/18) 或         │
│           残留值使得 lens 最终在遍历范围内出现 >15 的值            │
└────────────────────────────┬───────────────────────────────────┘
                             ↓
┌────────────────────────────────────────────────────────────────┐
│ Step 4: 触发 zng_inflate_table(LENS, copy->lens, copy->nlen,..)  │
│         → count_lengths(copy->lens, copy->nlen, count)           │
│         → 遍历 sym:0 → copy->nlen (最大286)                      │
│         → count[lens[sym]]++  如果 lens[sym] > 15 → OOB 写入 offs│
└────────────────────────────┬───────────────────────────────────┘
                             ↓
┌────────────────────────────────────────────────────────────────┐
│ Step 5: 污染 offs[] → work[] 越界 → 建表大循环 next 失控         │
│         → state->next 指向 codes[] 之外的非法地址                │
│         → 后续 DISTS 表建表时写入越界定                           │
└────────────────────────────────────────────────────────────────┘
```

### 前提条件

该利用链的前提是：**source state 的 `lens[]` 在 `have` 之后的残留区域中包含值 > 15**。这要求：

1. **第一次攻击**：使用另外的手段（例如 heap spray、之前的数据流解析）在 `state->lens[have..319]` 中留下恶意值
2. **inflateCopy 复制**：这些残留值通过 `memcpy` 完整复制到 `copy->lens[]`
3. **第二次攻击**：在 copy 上触发建表，使 `count_lengths` 遍历到恶意 lens 值

在纯 deflate 流解析的正常路径中，`lens[0..nlen+ndist-1]` 被 CODELENS 循环逐一填充（每个值 ≤15），不会留下 >15 的值。但如果存在**之前的堆溢出**或其他内存损坏，`lens[]` 数组的内存区域可能已被污染。

## 总结：inflateCopy 与 count_lengths 的关系

| 维度 | 分析结论 |
|------|---------|
| **直接调用关系** | inflateCopy **不直接**调用 count_lengths。inflateCopy 复制 state，后续在 copy 上调用 inflate() 时可能间接触发 count_lengths。 |
| **传参来源** | count_lengths 的 `lens` 参数 = `copy->lens`，`codes` 参数 = `copy->nlen` 或 `copy->ndist`。两者都通过 inflateCopy 的 `memcpy` 完整复制自 source state。 |
| **最危险场景** | 在 CODELENS 状态中途进行 inflateCopy，此时 `lens[]` 部分填充、部分残留。残留值如 >15 将在后续建表时触发 OOB。 |
| **指针安全问题** | inflateCopy 中 `next` 指针重定位无边界检查。若 source->next 已越界，copy->next 保持越界。 |
| **lencode 边界问题** | 上界检查 `<= codes + ENOUGH - 1` 缺少一个元素宽度的保护，指向 `codes[ENOUGH]` 仍被误判为合法。 |
| **利用难度** | 单独利用较难（需要先污染 lens[] 残留值），但在内存损坏漏洞链中是关键的**状态传递环节**——将越界状态从 source 精确复制到 copy。 |

# inflateCopy 漏洞触发的前提条件

## 概述

`inflateCopy` (`inflate.c:1380-1414`) 在重定位 `lencode`、`distcode`、`next` 指针时存在**条件捆绑**缺陷：只检查了 `lencode` 是否在 `codes[]` 内，但同时对 `distcode` 执行相同的算术重定位，且 `next` 指针完全无边界检查。

触发此漏洞需要同时满足以下 **5 个条件**：

---

## 前提 1：存在"指针混合状态"

`inflateCopy` 在第 1401 行只检查 `lencode` 是否在 `codes[]` 内：

```c
if (state->lencode >= state->codes && state->lencode <= state->codes + ENOUGH - 1) {
    copy->lencode = copy->codes + (state->lencode - state->codes);     // ✅ 正确
    copy->distcode = copy->codes + (state->distcode - state->codes);   // ❌ 无条件重定位
}

// ❌ next 指针完全无边界检查
copy->next = copy->codes + (state->next - state->codes);
```

**要求**：`lencode` 在 `codes[]` 内（条件成立），而 `distcode` **不在** `codes[]` 内（被错误重定位为野指针）。

---

## 前提 2：必须经过"固定块 → 动态块"的块序列

两个块的顺序是必需的：

| 步骤 | 块类型 | 发生什么 |
|------|--------|----------|
| 第 1 块 | BTYPE=01 (固定 Huffman) | `fixedtables()` 设置 `lencode=lenfix`、`distcode=distfix`（两个都是全局表） |
| 第 2 块 | BTYPE=10 (动态 Huffman) | CODELENS 中 `inflate_table(CODES, ...)` 将 `lencode` **改写**为指向 `codes[]` 内部 |

此时形成混合状态：

```
lencode   → 指向 state->codes[] 内部   ✅ （条件成立）
distcode  → 仍然指向全局 distfix      ❌ （将被错误重定位）
```

**如果只有固定块或只有动态块，都无法形成这种混合状态。**

### fixedtables() 源码 (inflate.c:305-310)

```c
void Z_INTERNAL PREFIX(fixedtables)(struct inflate_state *state) {
    state->lencode = lenfix;   // 全局固定字面量/长度表
    state->lenbits = 9;
    state->distcode = distfix; // 全局固定距离表
    state->distbits = 5;
}
```

> `lenfix` 和 `distfix` 是编译时在 `inffixed_tbl.h` 中定义的全局 `const code[]` 数组，**不在** `state->codes[]` 内。

---

### 背景：DEFLATE 中的三种块类型

DEFLATE 协议（RFC 1951）定义了三种压缩数据块类型，由每个块头部的 3 个 bit（1 bit BFINAL + 2 bit BTYPE）标识：

| BTYPE | 名称 | 说明 |
|-------|------|------|
| 00 | 不压缩块 (Stored) | 数据以原始字节存储，不经过任何压缩 |
| 01 | 固定 Huffman 块 (Fixed) | 使用 RFC 1951 预定义的固定 Huffman 码表进行压缩 |
| 10 | 动态 Huffman 块 (Dynamic) | 使用压缩数据中自定义的 Huffman 码表进行压缩 |
| 11 | 保留/错误 | 不允许使用，遇到则报错 |

#### 固定 Huffman 块 (BTYPE=01)

**定义**：使用 DEFLATE 协议预先写死的 Huffman 码表，压缩器和解压器都内置了这份码表，无需在数据流中传输码表定义。

**固定字面量/长度码表**（`lenfix`，定义在 `inffixed_tbl.h`）：
- 0-143: 8 位码长
- 144-255: 9 位码长
- 256-279: 7 位码长
- 280-287: 8 位码长

**固定距离码表**（`distfix`，定义在 `inffixed_tbl.h`）：
- 所有 32 个距离码均为 5 位码长

**触发方式**（`inflate.c:741-749`）：
```c
case 1:  /* fixed block */
    PREFIX(fixedtables)(state);  // 设置 state->lencode = lenfix, state->distcode = distfix
    state->mode = LEN_;
```
当 `inflate()` 状态机处于 TYPEDO 状态（`inflate.c:733-757`），从输入流读取 BTYPE 字段：
- `BFINAL(1bit) + BTYPE(2bit)`，BTYPE = 01（二进制）→ 进入 `case 1`
- `fixedtables()` 将 `lencode` 和 `distcode` 同时指向**全局只读段**的静态数组
- 状态切换到 `LEN_` → `LEN`，直接解码 literals/lengths/distances

**优点**：开销小，无需传输码表定义，适合小数据或多次独立压缩的块。
**缺点**：压缩率通常不如动态 Huffman 块。

#### 动态 Huffman 块 (BTYPE=10)

**定义**：码表定义跟随在块头部之后传输，解压器需要先解析码表定义，再用它来解压数据。

**动态块的头部结构**（`inflate.c:767-807`，TABLE 状态）：

```
    HLIT (5 bit)  → 字面量/长度码数量 = HLIT + 257 (最大 286)
    HDIST (5 bit) → 距离码数量 = HDIST + 1 (最大 32)
    HCLEN (4 bit) → CLENS 码长数量 = HCLEN + 4 (最大 19)
    CLENS[]       → 每个 3 bit，解码后用 order[] 重排 → 得到 19 个 CLENS 码长
    ═══ 以上在 TABLE + LENLENS 状态中处理 ═══
    LIT/LEN 码长 → 用 CLENS 作为码表解码，数量 = nlen = HLIT + 257
    DIST 码长    → 用 CLENS 作为码表解码，数量 = ndist = HDIST + 1
    ═══ 以上在 CODELENS 状态中处理 ═══
    构建 LENS 码表 → inflate_table(LENS, state->lens, state->nlen, ...)  → lencode 被重写
    构建 DISTS 码表 → inflate_table(DISTS, state->lens+nlen, state->ndist, ...) → distcode 被重写
    ═══ 以上在 CODELENS 状态的阶段 B 中处理 ═══
```

**触发方式**（`inflate.c:750-753`）：
```c
case 2:  /* dynamic block */
    state->mode = TABLE;
```
当 BTYPE = 10（二进制）→ 进入 `case 2`，状态切换到 `TABLE` → `LENLENS` → `CODELENS` → `LEN_`。

**优点**：可以针对数据特性优化码表，压缩率高。
**缺点**：需要传输码表定义，头部开销更大。

#### 为什么"固定块 → 动态块"序列对漏洞至关重要

| 块序列 | lencode | distcode | 是否产生混合状态 |
|--------|---------|----------|-----------------|
| 只有固定块 | `lenfix`（全局） | `distfix`（全局） | ❌ 两者一致在全局段 |
| 只有动态块 | `codes[]`（堆） | `codes[]`（堆） | ❌ 两者一致在堆上 |
| 固定块 → 动态块 | `codes[]`（堆） | `distfix`（全局） | ✅ 混合状态！ |

关键原因：
1. **固定块**的 `fixedtables()` 同时设置 `lencode` 和 `distcode` 为全局表——两者**同时**被设置，没有时间差
2. **动态块**的 LENLENS 状态（第 830-831 行）只将 `lencode` 改写为 `codes[]` 内部，`distcode` 保持不变
3. 只有**固定块先执行**（设定 `distcode = distfix`），然后**动态块再执行**（只改写 `lencode`），才能让 `distcode` 停留在全局段

**如果动态块在前、固定块在后**：动态块结束时 `inflate_table(LENS/DISTS)` 会将 `distcode` 也重写到 `codes[]` 内（第 911-914 行），之后固定块的 `fixedtables()` 会同时把两个指针都改回全局表——不会产生混合状态。

---

## 前提 3：输入数据必须在 CODELENS 阶段枯竭

CODELENS 状态有两个阶段：

```
阶段 A: inflate_table(CODES, ...)     ← 执行后 lencode → codes[]
阶段 B: inflate_table(LENS, ...)      ← 执行后 lencode、distcode 都会被重写为 codes[] 内部
         inflate_table(DISTS, ...)
```

`inflate.c:898-920`（阶段 B 的代码）：
```c
state->lencode = (const code *)(state->next);
state->lenbits = MAX_LEN_ROOT_BITS;
ret = zng_inflate_table(LENS, state->lens, state->nlen,
                        &(state->next), &(state->lenbits), state->work);
// ✅ lencode 被正确重写为指向 copy->codes[] 内部

state->distcode = (const code *)(state->next);
state->distbits = 9;
ret = zng_inflate_table(DISTS, state->lens + state->nlen, state->ndist,
                        &(state->next), &(state->distbits), state->work);
// ✅ distcode 也被正确重写为指向 copy->codes[] 内部
```

**如果阶段 B 完成，`distcode` 也会被重写到 `codes[]` 内，混合状态被"修复"，漏洞无法触发。**

**要求**：输入数据必须在阶段 A 之后、阶段 B 之前耗尽（`NEEDBITS()` → `PULLBYTE()` 失败 → `inflate()` 返回 `Z_OK`）。

---

## 前提 4：用户必须在此时调用 `inflateCopy()`

```c
// source stream 恰好处于 CODELENS 混合状态
zng_inflateCopy(&dest, &source);

// inflateCopy 内部：
// lencode 在 codes[] 内 → 条件成立
// distcode 指向 distfix → 被错误计算为: copy->codes + (distfix - state->codes)
// → distcode 成为指向 copy->codes[] 之外极远地址的野指针
```

### 野指针的具体计算

```
state->distcode = distfix          // 全局地址（如 0x400000）
state->codes                        // 堆上的内联数组地址（如 0x7f0000000000）

偏移量 = distfix - state->codes    // 极大的负数（在无符号运算中变为极大的正数）

copy->distcode = copy->codes + 偏移量  // → 指向 copy->codes[] 之外的地址
```

---

## 前提 5：`next` 指针也必须可重定位

第 1405 行无条件执行重定位：

```c
copy->next = copy->codes + (state->next - state->codes);
```

虽然 CODELENS 状态下 `next` 通常指向 `codes[]` 内部，但如果 `next` 已被污染（例如通过 `lens[]` 越界值驱动 `inflate_table` 产生越界的 `next`），则此重定位也会产生野指针。

**要求**：`next` 在 `codes[]` 的有效范围内，否则自身也会产生额外的问题。

---

## 完整条件链

```
前提 1: inflateCopy 的条件捆绑缺陷（只检查 lencode，不对 distcode 和 next 做独立检查）
         ↓
前提 2: BTYPE=01(固定块) → fixedtables() → lencode=lenfix, distcode=distfix
         ↓
前提 3: BTYPE=10(动态块) → inflate_table(CODES) → lencode 改写为 codes[] 内部
         ↓
前提 4: 数据在 inflate_table(LENS/DISTS) 之前枯竭 → distcode 仍指向 distfix
         ↓
前提 5: 此时调用 inflateCopy() → 条件成立，distcode 被算术重定位为野指针
```

**任何一个前提不满足，均无法触发 `distcode` 野指针。**
