API 前置条件缺失（missing precondition check）类漏洞

程序在调用某个 API 或执行某个关键操作之前，没有检查必须满足的条件，导致攻击者可以在“不应该发生”的状态下调用它，从而触发安全问题。

它属于一种逻辑漏洞（Logic Vulnerability），不是传统的内存破坏漏洞（如 UAF、栈溢出），更多出现在软件接口设计、权限控制、状态管理、资源管理中。

常见漏洞类型

类型1：权限检查缺失

类型2：状态检查缺失

类型3：生命周期检查缺失

类型4：资源状态检查缺失

zng_inflate_table() 的函数注释（第 195-198 行）明确写道：

This routine assumes, but does not check, that all of the entries in lens[] are in the range 0..MAXBITS. The caller must assure this.

换言之，调用者有责任保证 lens[] 中的值合法。分析所有调用路径：

路径 1：从合法 deflate 流解码（正常路径）— 不可触发

zng_inflate_table() 的合法调用链位于 inflate.c 的 LENLENS 和 CODELENS 状态：

在合法 deflate 数据流中，state->lens[] 的所有值都被限制在 0~15 范围内，无法触发越界。

路径 2：直接调用 zng_inflate_table() 并传入恶意 lens[] — 可触发（PoC 场景）

如果攻击者能够绕过头文件封装、直接调用 zng_inflate_table(LENS, lens, 286, ...)，并在 lens[] 中嵌入值 16，则可在不经过任何 deflate 流解析逻辑的情况下触发越界。这是 PoC (poc_stage_a.c) 使用的方式：

路径 3：通过 CLENS Huffman 表”有毒解码”间接触发 — 理论可行

虽然在合法流中 here.val 不会直接输出 > 15，但 CLENS 的码长表 state->lens[0..18] 先经过 zng_inflate_table(CODES, ...) 构建成 lencode 表。如果攻击者能够：

  1. 先用其他手段污染 state->lencode 表（如内存损坏、堆溢出等）
  2. 使得后续 CODELENS 解码时 here.val 被解为 16~255 之间的某个值

则 state->lens[state->have++] = here.val 可能写入 > 15 的值，进而在后续调用 zng_inflate_table(LENS, ...) 时触发 count 越界。

路径 4：通过 nlen / ndist 字段溢出 — 理论可行

deflate 头中的 HLIT 和 HDIST 字段分别指定 LENS 和 DISTS 符号数：

  • HLIT（5 位）：字面量/长度码数 = HLIT + 257，最大 286
  • HDIST（5 位）：距离码数 = HDIST + 1，最大 32

如果攻击者在 deflate 流头中设置了合法的 HLIT/HDIST（不触发错误），但同时在后面的码长数据中通过某种手段使 state->lens[] 在索引 ≥ 对应 codes 计数的位置被填充为 > 15 的值，虽然这些条目不参与解码，但它可能影响 count_lengths() 的遍历范围。

触发条件总结

条件 可行性 说明
合法 deflate 流 ❌ 不可行 deflate 流解析路径中所有 lens 赋值都被限制在 0~15
直接调用 zng_inflate_table() 传恶意 lens[] ✅ 可行 需要攻击者能直接调用该内部函数（PoC 场景）
CLENS Huffman 表中毒 ⚠️ 理论可行 需要先有其他漏洞污染 lencode 表，再触发 CODELENS 解码
内存损坏先于 count_lengths() ⚠️ 理论可行 需要先有其他漏洞（堆/栈溢出）修改 state->lens[] 的值

核心结论：该漏洞在正常 deflate 数据流解析路径中不可触发。它本质上是 API 前置条件缺失（missing precondition check）类漏洞，仅当调用者未遵守”lens[] 所有值必须 ≤ MAX_BITS”这个未在代码中强制执行的前置条件时，才会引发栈越界。由于 zng_inflate_table() 是 Z_INTERNAL 可见性的内部函数，直接暴露给外部攻击者的面较小，但如果与内存损坏漏洞串联，可以作为利用链中的一环。

攻击链

修复建议

方案 A：在 count_lengths() 入口添加 bounds check

方案 B：在 zng_inflate_table() 入口提前校验

推荐方案 A + B 结合：防御性编程，两层防护。方案 A 防止 count_lengths 被其他潜在调用者滥用；方案 B 为 zng_inflate_table 提供入口级保护。

功能概述

inflateCopy 的作用是深度复制一个 inflate 解压流的状态到另一个流：

  1. 复制 z_stream 结构体本身的全部字段
  2. 分配新的 window + state（通过 alloc_inflate()）
  3. 完整复制 inflate_state 结构体（memcpy）
  4. 重定位内部指针：lencode、distcode、next（它们指向 codes[] 数组内部）
  5. 复制滑动窗口数据

场景 A：复制时处于 CODELENS 状态（最危险）

场景 B：复制时处于 LEN 状态（建表已完成）

inflateCopy 指针重定位中的安全问题

问题 #1：next 指针无边界检查

与 lencode/distcode 的边界检查对比：

如果 state->next 已经因为 count_lengths 的 OOB → offs[] 污染 → work[] 越界 → 建表大循环中 next 跳转到异常位置，那么：

  1. copy->next 将保留一个指向 copy->codes 数组之外的野指针
  2. 后续在 copy 上调用 inflate() 时，如果触发新的动态块解码，zng_inflate_table() 会从 copy->next 指向的越界地址写入 Huffman 表条目
  3. 这将导致堆越界写入

问题 #2：lencode 边界检查的上界错误

codes[ENOUGH] 的有效索引范围是 [0, ENOUGH-1]。检查使用 <= codes + ENOUGH - 1 意味着当 lencode == codes + ENOUGH 时会被认为合法，但实际上已经越界一个 code 元素。

问题 #3：lens[320] 的内容被完全复制

lens[320] 包含在内。如果在 CODELENS 状态复制（have 未达到 nlen + ndist），部分 lens 条目来自 source 流的先前输入，部分为未初始化/历史残留值。这些值在 copy 上继续 inflate 时将被传入 count_lengths(lens, nlen, count)。

如果 lens 中包含 >MAX_BITS(15) 的值（无论来源），count_lengths 将发生 OOB 写入。

inflateCopy 与 count_lengths 漏洞的串联利用

利用链

前提条件

该利用链的前提是：source state 的 lens[] 在 have 之后的残留区域中包含值 > 15。这要求：

  1. 第一次攻击：使用另外的手段（例如 heap spray、之前的数据流解析）在 state->lens[have..319] 中留下恶意值
  2. inflateCopy 复制：这些残留值通过 memcpy 完整复制到 copy->lens[]
  3. 第二次攻击：在 copy 上触发建表，使 count_lengths 遍历到恶意 lens 值

在纯 deflate 流解析的正常路径中，lens[0..nlen+ndist-1] 被 CODELENS 循环逐一填充（每个值 ≤15），不会留下 >15 的值。但如果存在之前的堆溢出或其他内存损坏，lens[] 数组的内存区域可能已被污染。

总结：inflateCopy 与 count_lengths 的关系

维度 分析结论
直接调用关系 inflateCopy 不直接调用 count_lengths。inflateCopy 复制 state，后续在 copy 上调用 inflate() 时可能间接触发 count_lengths。
传参来源 count_lengths 的 lens 参数 = copy->lens，codes 参数 = copy->nlen 或 copy->ndist。两者都通过 inflateCopy 的 memcpy 完整复制自 source state。
最危险场景 在 CODELENS 状态中途进行 inflateCopy，此时 lens[] 部分填充、部分残留。残留值如 >15 将在后续建表时触发 OOB。
指针安全问题 inflateCopy 中 next 指针重定位无边界检查。若 source->next 已越界，copy->next 保持越界。
lencode 边界问题 上界检查 <= codes + ENOUGH - 1 缺少一个元素宽度的保护，指向 codes[ENOUGH] 仍被误判为合法。
利用难度 单独利用较难（需要先污染 lens[] 残留值），但在内存损坏漏洞链中是关键的状态传递环节——将越界状态从 source 精确复制到 copy。

inflateCopy 漏洞触发的前提条件

概述

inflateCopy (inflate.c:1380-1414) 在重定位 lencode、distcode、next 指针时存在条件捆绑缺陷：只检查了 lencode 是否在 codes[] 内，但同时对 distcode 执行相同的算术重定位，且 next 指针完全无边界检查。

前提 1：存在”指针混合状态”

要求：lencode 在 codes[] 内（条件成立），而 distcode 不在 codes[] 内（被错误重定位为野指针）。

前提 2：必须经过”固定块 → 动态块”的块序列

两个块的顺序是必需的：

步骤 块类型 发生什么
第 1 块 BTYPE=01 (固定 Huffman) fixedtables() 设置 lencode=lenfix、distcode=distfix（两个都是全局表）
第 2 块 BTYPE=10 (动态 Huffman) CODELENS 中 inflate_table(CODES, ...) 将 lencode 改写为指向 codes[] 内部

此时形成混合状态：

如果只有固定块或只有动态块，都无法形成这种混合状态。

fixedtables() 源码 (inflate.c:305-310)

lenfix 和 distfix 是编译时在 inffixed_tbl.h 中定义的全局 const code[] 数组，不在 state->codes[] 内。

背景：DEFLATE 中的三种块类型

DEFLATE 协议（RFC 1951）定义了三种压缩数据块类型，由每个块头部的 3 个 bit（1 bit BFINAL + 2 bit BTYPE）标识：

BTYPE 名称 说明
00 不压缩块 (Stored) 数据以原始字节存储，不经过任何压缩
01 固定 Huffman 块 (Fixed) 使用 RFC 1951 预定义的固定 Huffman 码表进行压缩
10 动态 Huffman 块 (Dynamic) 使用压缩数据中自定义的 Huffman 码表进行压缩
11 保留/错误 不允许使用，遇到则报错

固定 Huffman 块 (BTYPE=01)

定义：使用 DEFLATE 协议预先写死的 Huffman 码表，压缩器和解压器都内置了这份码表，无需在数据流中传输码表定义。

固定字面量/长度码表（lenfix，定义在 inffixed_tbl.h）：

  • 0-143: 8 位码长
  • 144-255: 9 位码长
  • 256-279: 7 位码长
  • 280-287: 8 位码长

固定距离码表（distfix，定义在 inffixed_tbl.h）：

  • 所有 32 个距离码均为 5 位码长

触发方式（inflate.c:741-749）：

当 inflate() 状态机处于 TYPEDO 状态（inflate.c:733-757），从输入流读取 BTYPE 字段：

  • BFINAL(1bit) + BTYPE(2bit)，BTYPE = 01（二进制）→ 进入 case 1
  • fixedtables() 将 lencode 和 distcode 同时指向全局只读段的静态数组
  • 状态切换到 LEN_ → LEN，直接解码 literals/lengths/distances

优点：开销小，无需传输码表定义，适合小数据或多次独立压缩的块。
缺点：压缩率通常不如动态 Huffman 块。

动态 Huffman 块 (BTYPE=10)

定义：码表定义跟随在块头部之后传输，解压器需要先解析码表定义，再用它来解压数据。

动态块的头部结构（inflate.c:767-807，TABLE 状态）：

触发方式（inflate.c:750-753）：

当 BTYPE = 10（二进制）→ 进入 case 2，状态切换到 TABLE → LENLENS → CODELENS → LEN_。

优点：可以针对数据特性优化码表，压缩率高。
缺点：需要传输码表定义，头部开销更大。

为什么”固定块 → 动态块”序列对漏洞至关重要

块序列 lencode distcode 是否产生混合状态
只有固定块 lenfix（全局） distfix（全局） ❌ 两者一致在全局段
只有动态块 codes[]（堆） codes[]（堆） ❌ 两者一致在堆上
固定块 → 动态块 codes[]（堆） distfix（全局） ✅ 混合状态！

关键原因：

  1. 固定块的 fixedtables() 同时设置 lencode 和 distcode 为全局表——两者同时被设置，没有时间差
  2. 动态块的 LENLENS 状态（第 830-831 行）只将 lencode 改写为 codes[] 内部，distcode 保持不变
  3. 只有固定块先执行（设定 distcode = distfix），然后动态块再执行（只改写 lencode），才能让 distcode 停留在全局段

如果动态块在前、固定块在后：动态块结束时 inflate_table(LENS/DISTS) 会将 distcode 也重写到 codes[] 内（第 911-914 行），之后固定块的 fixedtables() 会同时把两个指针都改回全局表——不会产生混合状态。
